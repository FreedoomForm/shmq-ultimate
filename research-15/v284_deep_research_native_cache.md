# v284 deep research: eliminate redundant expanded INT4 state on the native packed path

The preserved original MixLLM implementation prepares `weight_int4` directly in the persistent CUTLASS interleaved packed layout. Its `LinearMixLLM.__init__` calls `interleave_uint4_for_cutlass` and stores the packed tensor; the original path does not create a signed expanded `[n4, K]` INT8 copy for its native prefill GEMM.

The current SHMQ implementation correctly added the same persistent interleaved cache, but `ThreeLevelLinear._apply()` and `ThreeLevelLinear.from_weight()` still eagerly call both `prepare_sm75_prefill_cache()` (signed expanded INT4) and `prepare_sm75_prefill_int4()` (native packed INT4). The backend then also requests `_expanded_int4_for_prefill()` before selecting the cached-v3 native packed launcher. In the native packed branch the CUDA scheduler chooses `weight_int4_interleaved` and does not read `expanded_int4`; the expanded tensor is retained for the legacy v2 fallback and for compatibility with callers lacking the interleaved cache.

This creates a memory-preservation seam: make expanded INT4 lazy when the native interleaved cache is available, while retaining the expanded fallback for modules without native packed state and preserving the ABI-compatible empty placeholder for decode and empty INT4 partitions. The change must not remove the expanded cache API, alter arithmetic, alter the benchmark, alter model/quality checks, or change the v2 fallback. The memory report should honestly show zero `expanded_int4_bytes` for a native-only prepared module and the same nonzero value for fallback-only preparation.

The required local contracts are: native v3 still receives the persistent interleaved tensor and cached metadata; v2 fallback still receives signed expanded INT4; cache invalidation on `.to()`, state loading, and in-place tensor mutation remains correct; decode continues to skip expansion; and all existing correctness, quality, timing-integrity, and memory fields remain present. This is a source-level candidate only; no T4 performance claim is made until Kaggle gates run.
