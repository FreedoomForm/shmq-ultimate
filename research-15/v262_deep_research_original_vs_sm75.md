# v262 deep research: replace only the FP16 partition kernel with cuBLAS where it is legal

The rejected v261 cached-metadata run improved Qwen mixed rows=128 E2E from `0.226004x` to `0.264976x`, while timing-integrity remained valid. The result shows caller-stream metadata preparation was a real cost, but the dominant remaining gap is the FP16 partition and its interaction with the integer branches.

The original Microsoft MixLLM launcher uses one staged INT4 runner and one staged INT8 runner on persistent auxiliary streams, then joins both events on the caller stream. SHMQ preserves that topology for integer partitions. The relevant mismatch is the FP16 partition: SHMQ's `three_level_tensorcore_kernel` uses a custom WMMA path in the same monolithic kernel family, whereas the original two-level implementation has no FP16 partition. Therefore the original source does not provide a direct FP16 reference path, but it does establish the safe stream rule: any replacement must enqueue on the caller stream and be joined only after the integer completion events.

| Candidate | Why it is considered | Why it is safe or unsafe |
|---|---|---|
| Direct packed INT4 CUTLASS | Would remove SHMQ's expanded INT8 cache and move toward upstream layout. | Unsafe for this iteration: the vendored SM75 headers lack upstream `OpMultiplyAddMixedAndShuffledInputUpcast`; the only legal SM75 native pair path is a custom 8x8x32 construction and its mixed large-M result was already slower. |
| cuBLAS for FP16 partition | Uses a supported SM75 dense FP16 GEMM for the exact FP16 rows and weights, preserving the 16-bit model weights and FP32-accumulate/FP16-output semantics expected by the ABI. It may remove the custom per-tile shared-memory and scatter overhead for the FP16 branch. | Safe if restricted to `n16 > 0`, preserving the same `input_fp16`, `weight_fp16`, `indices_fp16`, output dtype, and row-major scatter. It must enqueue on the caller stream after the integer fork and remain before the caller waits on integer completion. It does not remove any partition or alter quantized arithmetic. |
| cuBLAS for INT4/INT8 | Dense integer GEMM might use Tensor Cores. | Not selected: per-group activation and weight scales plus INT4 zero correction require a fused epilogue or one GEMM per 128-column group; a naive cuBLAS substitution would change arithmetic/dataflow or add many launches. |

The v262 implementation will add a small `run_fp16_partition_cublas` helper that computes the FP16 partition as `at::mm(input_fp16, weight_fp16.t())` on the caller stream and scatters into `output` by `indices_fp16`. It will be used only from the rows>=32 overlap branch and only for nonempty FP16 partitions. The existing direct WMMA path remains unchanged for rows<32, preserving the validated decode/small-prefill geometry. If local tests or the Kaggle correctness gate expose a semantic mismatch, the candidate is rejected and the current accepted baseline remains untouched.
