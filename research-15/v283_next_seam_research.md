# v283 next-seam primary-source research

## Question

Which architecture seam can replace the rejected expanded-INT4 production path without repeating the unsafe synthetic-k32 adapter, while preserving the exact 4/8/16 partition ABI and honest Qwen/T4 gates?

## Primary-source findings

| Finding | Evidence | Design consequence |
|---|---|---|
| Microsoft MixLLM creates persistent INT4 and INT8 auxiliary streams, a fork event, and completion events once per singleton launcher. | The upstream `LinearMixLLM` constructor creates `local_stream_int4`, `local_stream_int8`, `fork_stream_event`, and two completion events in `mix_mma_multistage.cuh`; `gemm()` records the caller-stream fork, waits on it in each precision stream, launches each partition, records completion, then makes the caller stream wait. [1] | Retain SHMQ's persistent stream/event ownership and fork/join. Do not serialize the integer branches or add per-call stream creation. |
| Upstream uses the packed `matrix_B_interleaved` buffer directly in the INT4 CUTLASS testbed and keeps INT8 as a separate input buffer. | In upstream `gemm()`, `mixllm_int4.run(... matrix_B_interleaved ...)` and `mixllm_int8.run(... matrix_B_int8 ...)` are launched independently; the launcher validates the packed tensor shape `size(1)*2 == K`. [1] | A production INT4 branch must consume the module-owned interleaved packed tensor directly. The current expanded signed-INT8 cache is a correctness fallback, not a bandwidth-equivalent replacement. |
| Upstream's interleave is a two-stage transform: first a 32-element permutation, then an 8-element `[0,4,1,5,2,6,3,7]` permutation, followed by nibble packing. | The upstream `interleave_uint4_for_cutlass()` implements these exact permutations and `pack_uint4_for_cutlass()`. [2] | SHMQ's mirrored interleave should remain the canonical packed-weight contract. Any native loader must be proven against this contract, not against a newly invented layout. |
| Official CUTLASS's Turing INT4 MMA is `m8n8k32` with `int4b_t` inputs and int32 accumulation; INT8 is `m8n8k16`. | NVIDIA's CUTLASS Turing documentation lists `8x8x32 int4b_t x int4b_t -> int32_t` and `8x8x16 int8b_t x int8b_t -> int32_t`, and shows the `mma.sync.aligned.m8n8k32.row.col.s32.s4.s4.s32` instruction. [3] | The legal native design must represent a real m8n8k32 packed operation. A k32 policy wrapped around actual m8n8k16 fragments is not an acceptable production design. |
| Official CUTLASS's SM75 INT4 example uses a hierarchical threadblock/warp/MMA composition and a two-stage pipeline. | NVIDIA documents a 128x128x128 threadblock, 64x64x128 warp, 8x8x32 instruction, and `NumStages=2` for a Turing INT4 convolution example; it explains that larger tiles increase data reuse but can under-occupy small problems. [3] | The next branch should be a real CUTLASS-style loader/MMA composition or an exact equivalent with independently verified shared-memory layout, not a permutation-only patch to the old adapter. Tile selection must be shape-guarded. |
| Official CUTLASS's Turing GEMM example explicitly separates global->register->shared->register->MMA->register->global stages, and uses Sm75 with a 2-stage pipeline. | The first-party `turing_tensorop_gemm.cu` describes the hierarchy and instantiates `Sm75`, `ShapeMMAOp=GemmShape<8,8,16>` for INT8, and `NumStages=2`; it also calls `can_implement()` before initialization and launch. [4] | A safe SM75 implementation needs an explicit legal iterator/layout contract and a `can_implement`-equivalent shape guard. It must not silently select an unsupported branch. |
| Official documentation recommends 128-bit aligned/vectorizable tensors and says smaller alignment is supported but slower. | CUTLASS Turing documentation recommends 128-bit alignment and channel/filter multiples of 32 for efficient vector access. [3] | The branch should be restricted initially to widths/channels satisfying alignment and tile divisibility, with all other shapes routed to the existing fallback. |
| SHMQ's direct pair kernel is not equivalent to the upstream CUTLASS hierarchy. | In `three_level_sm75.cu`, `sm75_int4_pair_gemm_kernel` stages a 32x32 input tile and channel tile, uses `wmma::load_matrix_sync` with `m8n8k32`, then manually reinterprets only `x[0]` into `PairProbe*` fragments before two custom MMA calls. The production path currently forces `use_fused_int4=false` in `run_unified_prefill()`. | v283's probes prove the isolated fragment/load contract for tested values but not a production speed path. Do not re-enable it wholesale. If used at all, add a narrow live dispatch and compare its output to the fallback on real partition shapes before measuring performance. |

## Selected next seam

The most defensible seam is **a guarded native packed INT4 path behind the existing integer overlap**, implemented with the original packed tensor and a self-consistent SM75 `m8n8k32` dataflow. The first version should be narrow: only large, aligned prefill shapes where the loader can cover complete 32-row/32-channel tiles and where each output element has one writer. The branch must retain the expanded CUTLASS fallback for all other shapes and on any explicit capability failure. It must use the existing fork/event architecture, module-owned packed/scale/zero/index buffers, and exact 4/8/16 scatter semantics.

The isolated v283 pair kernel is not yet sufficient evidence for this seam because it is unreachable in normal production inference. If the implementation reuses any part of it, the dispatch must be guarded by a new contract, and T4 probes must cover rows>=32, channels>=128, tails, mixed 4/8/16 partitions, and output index uniqueness. Performance is admissible only after native correctness, timing integrity, allocator/memory, full-model quality, vLLM production, and mixed prefill/decode gates pass under unchanged benchmark settings.
