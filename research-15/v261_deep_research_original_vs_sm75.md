# v261 deep research: cached CUTLASS metadata for mixed large-M

The source-verified v260 run passed timing-integrity but measured only `0.226004x` Qwen mixed rows=128 end-to-end speedup, so redundant allocator bookkeeping is not the bottleneck. The next seam was compared against the original Microsoft MixLLM implementation.

| Concern | Original MixLLM | SHMQ SM75 | Consequence |
|---|---|---|---|
| INT4 operand | `LinearMixLLM.interleave_uint4_for_cutlass` performs the two upstream permutations once, then packs a `uint4b_t` CUTLASS-ready tensor. | `ThreeLevelLinear` stores checkpoint-packed `uint8` plus a separately expanded signed INT8 `[n4,K]` cache for prefill. | A direct packed-INT4 SM75 CUTLASS port would require an operator family that is not present in the vendored SM75 headers. The upstream `OpMultiplyAddMixedAndShuffledInputUpcast` and its SM80 custom header are SM80-side only. |
| Large-M dispatch | The original launcher sends INT4 and INT8 staged GEMMs to persistent auxiliary streams after one fork event, with metadata already in the kernel-compatible layout. | SHMQ's Python dispatcher sends all mixed rows>=32 through the measured v188/v2 path. The v2 path creates `scale_int4`, `zero_int4`, and `scale_int8` transposes on the caller stream before the fork unless cached pointers are supplied. | Mixed large-M still pays avoidable metadata preparation and uses the old adapter even though SHMQ already owns a cache with the required `[groups,channels]` layout. |
| Cached ABI | Not applicable as a separate SHMQ layer; upstream module preparation is the canonical layout. | `prepare_sm75_prefill_metadata` creates and invalidates the three transposed tensors across device/state changes. `_three_level_linear_v3_unchecked` passes those tensors directly into the same CUDA core, where `begin_integer_prefill_overlap` skips the caller-stream transposes. | The v3 seam is a real internal adapter seam and can be tested without changing arithmetic or quality. |
| Historical evidence | — | v220 tested the cached-v3 mixed path before v258 corrected all production output stores to FP16 and before the v260 record optimization. It reported `0.2686x` and timing ratio `1.4156`; that old result is not a clean test of the current ABI. | Re-test cached metadata once with the current half-output source. Keep only if all gates, including timing-integrity, pass. |

The candidate is therefore deliberately narrow: change only `_use_v188_mixed_prefill_path` so mixed rows>=32 reaches the existing cached-metadata v3 adapter. No direct packed INT4 claim is made for SM75, no quality threshold changes, no benchmark changes, and no computation is removed. If this fails, the direct packed route should remain research-only until a legal SM75 mixed-input implementation is independently proven at the PTX/WMMA level.

Primary local sources: `/tmp/original-MixLLM/mixllm/nn/modules/linear.py` lines 64-157, `/tmp/original-MixLLM/mixllm/kernels/mix_mma_multistage.cuh` lines 188-258, SHMQ `three_level_linear.py` lines 92-137, SHMQ `sm75_backend.py` lines 210-290, and SHMQ `three_level_sm75.cu` lines 1133-1175 and 1352-1395.
